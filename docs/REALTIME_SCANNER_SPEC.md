이 문서는 CLAUDE.md의 절대 금지 사항을 그대로 따른다: `app.py`/`database.py`/
`performance.py`/`price_data.py` 무변경, `db/jarvis.sqlite3` 무변경, 기존 report

수행**한다.

## 1. 목적

장중 스냅샷은 단타/스윙 판단을 보조하기 위한 **숫자 확인 도구**다.

- AI가 바로 추천하는 기능이 아니다.
- 자동매매 기능이 아니다.
- 먼저 장중 상태를 숫자로 **기록**하고, 나중에 성과(`performance.py`의 사후 검증)와
  비교하기 위한 기반 데이터를 쌓는 것이 목적이다.
- 기존 "브리핑 붙여넣기"가 사람이 서술형으로 판단을 기록하는 도구라면, 장중 스냅샷은
  그 판단의 배경이 된 숫자를 같이 남겨서 나중에 "그때 숫자가 실제로 어땠는지" 대조할 수
  있게 하는 보조 기록 도구다.

## 5. 계산식

| 지표 | 계산식 |
|---|---|
| 전일 대비 상승률 | `(현재가 - 전일종가) / 전일종가 * 100` |
| 시가 대비 위치 | `(현재가 - 시가) / 시가 * 100` |
| 장중 고점 대비 밀림률 | `(현재가 - 장중고가) / 장중고가 * 100` |
| 장중 저점 대비 회복률 | `(현재가 - 장중저가) / 장중저가 * 100` |
| 시총 대비 거래대금 | `거래대금 / 시가총액 * 100` |
| 지수 대비 상대강도 | `종목 상승률 - KOSPI 상승률` |

이 계산식들은 전부 화면 표시/기록용이며, `performance.py`의 사후 검증 계산(진입가 규칙,
1/3/5/10/20일 수익률, 기준지수 대비 초과수익률)과는 **별개의 값**이다. 장중 스냅샷 계산식이
`performance.py`를 대체하거나 수정하지 않는다.

## 8. 첫 버전 화면 구상

- **탭 이름**: 장중 스냅샷
- **버튼**: 현재 상태 입력/조회

  직접 타이핑하거나, 붙여넣기 형태로 넣는 것도 가능하게 — 이번 설계에서는 방식을 확정하지

화면 구성(안):
1. 외부 환경 입력 영역 (3번 항목의 8개 지표)

## 11. 일봉 기본값 자동조회 후보 조사 (2026-07-06, 조사만·구현 없음)

7단계("가능한 데이터만 준실시간 조회 도입")의 사전 조사. **코드는 건드리지 않았고**,
읽기 전용으로 각 라이브러리를 직접 호출해서 실제로 어떤 필드가 나오는지 확인했다
(005930 기준). 결론만 먼저: **네이버 금융 스크래핑은 이 프로젝트의 기존 규칙
(CLAUDE.md/PROJECT_SPEC.md "네이버/다음 등 시세 스크래핑 금지")에 이미 위배되므로
후보에서 제외**한다. 실질적으로는 pykrx와 yfinance/FinanceDataReader 중 선택하는
문제다.

### 필드별 제공 여부 (전일종가/시가/고가/저가/거래대금/시가총액)

| 항목 | pykrx | yfinance | FinanceDataReader |
|---|---|---|---|
| 시가/고가/저가/종가(전일종가로 활용) | O | O | O |
| 거래량 | O | O | O |
| **거래대금** | 직접 제공 안 함(`get_market_ohlcv_by_date`엔 없음, `get_market_trading_value_by_date` 등 별도 호출 필요) | 직접 제공 안 함 | 직접 제공 안 함 |
| **시가총액(일별)** | `get_market_cap_by_date` 함수는 있으나 **오늘 재현 테스트에서 반복적으로 오류**(`Expecting value: line 1 column 1` — 응답이 JSON이 아님) | 일별 과거값은 없음. `fast_info.market_cap`은 **현재 시점 스냅샷만** 제공 | 미제공 |

즉 세 라이브러리 전부 "거래대금"과 "일별 시가총액"을 곧바로 주지 않는다. 실제로
구현한다면 아래 근사식이 필요하다(1차 설계 메모, 아직 코드 없음).

- 거래대금(근사) = 거래량 × 종가 (실제 체결가 분포를 반영하지 못하는 근사치)
- 시가총액(근사) = 상장주식수 × 종가. 상장주식수는 yfinance의 `fast_info.shares`로
  비교적 안정적으로 얻을 수 있었다(005930 기준 6,566,563,106주, 정상 조회됨).

### 안정성/실제 재현 결과

- **pykrx**: 개별 종목 시가/고가/저가/종가/거래량 조회는 이번에도 정상 동작(기존
  `docs/DATA_TEST_RESULTS.md`와 일치). 하지만 `get_market_cap_by_date`는 오늘
  2회 재시도 모두 실패 — 이전에 이미 문서화된 KOSPI 지수 조회 실패와 같은 계열의
  불안정성으로 보인다. **KRX 비공식 엔드포인트를 그대로 호출하는 구조라 언제든
  깨질 수 있다는 근본 리스크**가 이번에도 재확인됐다.
- **yfinance**: OHLCV(시가/고가/저가/종가/거래량)와 `fast_info`(현재 시가총액,
  상장주식수)까지 전부 정상 응답. `docs/DATA_TEST_RESULTS.md`에서도 6개 대상
  전부 성공했던 유일한 라이브러리였고, 이번 조사에서도 가장 안정적이었다. 다만
  Yahoo 비공식 API를 쓰는 점은 pykrx와 근본적으로 유사한 리스크이나, 사용자층이
  훨씬 넓어 상대적으로 덜 취약하다.
- **FinanceDataReader**: OHLCV는 안정적으로 나오지만, 개별 종목에는 거래대금/
  시가총액 컬럼이 아예 없다(지수 데이터에는 있었지만 개별 종목에는 없음 — 이전
  조사에서 확인한 KS11의 Amount/MarCap 컬럼은 지수 전용이었다).
- **네이버 금융 스크래핑**: 기술 검토 이전에 **이미 금지된 방식**이라 비교 대상에서
  제외. (참고로 스크래핑 방식은 페이지 구조 변경 시 즉시 깨지고 차단 위험도 가장
  크므로, 규칙이 없었더라도 우선순위가 낮았을 것이다.)

### 결론 (구현 전 설계 메모, 승인 필요)

**yfinance를 기본, FinanceDataReader를 보조로 쓰는 현재 `price_data.py`의 기존
전략을 그대로 유지하는 것이 가장 안전**하다. pykrx는 개별 시가/고가/저가/종가
조회에는 계속 보조로 쓸 수 있지만, 이번 기능(거래대금/시가총액 자동 채움)에
필요한 `get_market_cap_by_date`가 오늘도 재현 가능하게 실패했으므로 **이 기능의
1차 구현에서는 배제**하는 것을 권장한다. 거래대금/시가총액은 근사식(거래량×종가,
상장주식수×종가)으로 채우는 방식을 다음 설계 단계에서 사용자와 다시 협의해야
한다 — 근사치라는 점을 화면에 명시해야 하며, 이 근사식 적용 여부와 `price_data.py`
변경 범위는 별도 승인 후 진행한다.
