## 0. 가장 먼저 알아야 할 원칙

이 방에서 세운 규칙이다. **어기면 화면이 거짓말을 한다.**

1. **재 보지 않은 값으로 순위를 매기지 않는다.** 좋아 보여도 실측에서 갈리지 않으면 뺀다.
2. **성적 옆에는 늘 기준선('아무 날이나 샀으면')을 적는다.** 오늘 살아남은 종목만 보고
   재기 때문에, 같은 종목으로 잰 기준선과 견줄 때만 치우침이 상쇄된다.
3. **진 것은 졌다고 적는다.** 낙폭 -30~-40% 갈래는 한국에서 기준선보다 못했고, 화면에
   그대로 적혀 있다.
4. **미국과 한국은 배점이 다르다.** 시장도 자료도 실측 결과도 다르다. 같은 자로 재면 안 된다.
5. 화면 문구·코드값·문서 숫자가 어긋나면 **시험이 먼저 깨지게** 묶어 두었다.

## 2. 남은 일 — 우선순위 순

### ① 상승장(신고가 눌림) 전용 배점 — **재기만 하고 코드에 안 넣음** ⬅ 여기부터

미국 10년치 3,250개 표본으로 이미 쟀다. 기준선 가운데 +6.25% · 100번 중 62번.

| 후보 | 실측 | 넣나 |
|---|---|---|
| 같은 테마 3개 이상 동반 | +18.94% · **78번** | ✅ 35점 |
| 최근 60일 40% 넘게 오름 | +15.98% · **70번** | ✅ 30점 |
| 눌린 폭 -5~-5.5% | +7.27% · 66번 | ✅ 15점 |
| 유동성 | — | ✅ 10점 |
| 변동성 | +12.18%(4% 넘음) · 62번 | ✅ 10점 |
| **거래대금 평소 위 연속** | 11일 이상 · **+0.98% · 53번** | ❌ **0점 (거꾸로)** |
| 기다린 날(3/4/5일) | 63/63/61번 | ❌ 차이 없음 |
| 50·200일선 위 | 전부 위 | ❌ **의미 없음**(신고가 종목은 정의상 100% 위) |

**낙폭과 정반대인 것 두 가지 — 반드시 기억할 것**
- 거래대금 연속: 낙폭에서는 좋고(67번) 상승장에서는 **나쁘다**(53번).
  상승장은 이미 신고가라 오래 실린 거래대금은 '늦었다'는 뜻이다.
- 최근 상승폭: 낙폭에서는 나쁘고(48번) 상승장에서는 **좋다**(70번).

**할 일**
1. `jarvis3_data`에 `breakout_score()` / `breakout_plan()` 추가(낙폭용 `crash_rebound_score`
   바로 옆에, 같은 모양으로). 배점은 위 표.
2. 상승장 표의 칸을 바꾼다 — **'거래대금(평소 위 연속)' 빼고 '최근 60일 상승폭' 넣기.**
   낙폭 표는 그대로 둔다.
3. 한국도 같은 검사를 따로 해서 배점을 잡는다(미국 값을 옮겨 적지 말 것).
   재는 판: `scratchpad/breakout_score.py`와 같은 방식, 자료는 `kr_daily.pkl`.

### ② 낙폭 전용 점수를 화면에 연결 — **데이터 층만 됨**

`crash_rebound_score()` / `crash_rebound_plan()`은 두 시장 모두 **만들어져 있고 값도 나온다**
(미국 KLAC 75.3점 '조건부 후보', 한국 한미반도체 81.8점). 그런데 **화면이 아직 기존
조건점수를 쓴다.** 낙폭 종목을 누르면 여전히 14~26점 '제외'가 뜬다.

바꿔야 할 세 곳(두 페이지 모두):
- **종목 선정 근거** 점수표 → `crash_rebound_score()["parts"]`
- **매수 심사 결과** → `crash_rebound_plan()` (기준가·손절 없음. "다음 거래일 시가에 사서
  N거래일 뒤 종가에 판다"로)
- **추천 근거 요약** 4칸 → 낙폭용 문구

들어가는 자리: 미국 `pages/2_자비스3.py`의 `_render_pullback_detail`,
한국 `pages/3_자비스4.py`의 `_render_pullback_detail`.
`st.session_state["j3_pullback_mode"]`/`j4_pullback_mode`가 `"crash"`인지 보고 갈라야 한다.

### ③ 나스닥 주봉 반등 신호 — **결론은 났고 화면에 안 넣음**

사용자 기준은 "MACD와 STC 둘 다 침체". 55년 주봉으로 24개 설정에서 재 봤다.

- **"둘 다 침체"만 보면 24개 중 23개에서 기준선보다 나빴다**(52~67번 vs 70번).
  침체는 하락장 한복판이지 반등 신호가 아니다.
- **"침체 + MACD 막대 3주 연속 커짐"은 24개 중 16개에서 기준선을 이겼고, 24개 전부에서
  침체만 볼 때보다 좋아졌다.** 방향이 일관되므로 설정 탓이 아니다.
- **다이버전스는 6개 설정 중 0개에서 이겼다.** 섞으면 오히려 나빠진다(77→71번). 쓰지 말 것.
- 빈도: 12/26 설정에서 55년에 28번 ≈ **2년에 한 번**. 사용자가 원한 "1~2년에 한 번"과 맞는다.

**막힌 것** — 숫자가 설정에 따라 59~81번으로 벌어진다. **사용자의 STC 설정값(23/50인지
다른 값인지)을 물어봐야** 사용자가 실제로 보는 화면과 같은 숫자를 낼 수 있다.
설정을 받기 전에는 화면에 넣지 말 것.

## 3. 손대면 안 되는 것 / 알고 있어야 할 함정

- **`test_bookmaker_data.py::PolymarketEventGroupingTests` 1건은 원래 깨져 있다.**
  이 방에서 건드리지 않은 파일이고, 작업 전부터 실패했다. 다른 실패와 혼동하지 말 것.
- **PowerShell `Set-Content -Encoding utf8`은 BOM을 넣는다.** 이 방에서 파일 9개에 BOM이
  들어갔다가 걷어냈다. 파이썬 파일을 고칠 때는 `Write`/`Edit` 도구나 파이썬으로 쓸 것.
- **PowerShell here-string(`@'...'@`)에 큰따옴표가 들어가면 git 인자가 쪼개진다.**
  커밋 메시지는 파일로 만들어 `git commit -F`로 넣을 것.
- **모듈 리비전(규칙 11)** — `jarvis3_data`/`jarvis4_data`/`method_help`/`mobile_ui`를 고치면
  그 파일의 `MODULE_REVISION`과 페이지의 `_REQUIRED_*_REVISION`을 **같이** 올린다.
  안 올리면 온라인에 옛 코드가 남는다(이 방에서 실제로 "설명서가 안 바뀐다"로 겪었다).
- **표를 새로 만들면** 페이지 `<style>`의 옆으로 밀기 목록 **세 곳**에 다 넣어야 한다.
  빠뜨리면 폰에서 칸이 세로로 쌓이고 값이 겹쳐 찍힌다.
- **화면이 열릴 때마다 두 번 그려진다**(쿠키 로그인 컴포넌트 탓). 첫 판을 `st.stop()`으로
  끊는 방법은 시도했다가 되돌렸다 — 쿠키가 막힌 곳에서 화면에 갇힌다.
  자세한 것: 메모리 `project_double_render_cookie_login`.
