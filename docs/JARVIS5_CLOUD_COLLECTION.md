# 자비스5 자료 수집 구조 (2026-07-24 도입)

자비스5(한국테마 선행감지)의 자료가 **어디서 어떻게 모이고 어디에 저장되는지**를
적어 둔다. 나중에 이 부분을 건드리는 사람이 "왜 이렇게 만들었나"를 알고 손대야 한다.

---

## 1. 왜 만들었나

자비스5는 장중 3분마다 네이버 전체 테마(266개)의 거래활동을 기록해, 어느 테마로
자금과 가격이 먼저 퍼지는지를 나중에 검증하려는 실험 화면이다. 기록이 촘촘해야
의미가 있다.

그런데 원래 구조는 `run_jarvis5_collector.bat`을 **사람이 켜 둔 동안만** 자료가
쌓였다. 컴퓨터를 껐다 켜면 자동으로 살아나지 않는다. 실제로 이런 일이 있었다.

| 날짜 | 수집 횟수 | 상황 |
|---|---|---|
| 2026-07-23 | 82회 (3분 간격) | 배치를 켜 뒀음 |
| 2026-07-24 | 5회 (간격 제각각) | 배치를 안 켬. 화면 버튼을 누른 것만 기록됨 |

사용자 요구는 "노트북을 안 켜도 자료가 모이고, 금요일에 끄고 월요일에 켜도 그 사이
자료가 있어야 한다. 돈은 들지 않아야 한다"였다.

---

## 2. 지금 구조

```
평일 장중
  GitHub Actions 컴퓨터 ──3분마다 네이버 수집──> 러너 안 임시 DB
                        ──10분마다 파일로 내보내 저장소에 커밋──> data/jarvis5/

사용자가 노트북을 켠 날
  자비스5_자료받기.bat  ──git pull──> data/jarvis5/
                        ──합치기──> db/jarvis5_theme_lead.sqlite3
  (또는 자비스5 화면의 '클라우드에 쌓인 자료 가져오기' 버튼)
```

관련 파일:

| 파일 | 하는 일 |
|---|---|
| `.github/workflows/jarvis5_collect.yml` | 클라우드 수집 일정과 커밋 |
| `jarvis5_collector.py` | 수집 루프. `--until`, `--export-dir`이 클라우드용 |
| `jarvis5_sync.py` | 하루치 내보내기·들여오기 |
| `자비스5_자료받기.bat` | 내려받아 합치기 (사용자용) |
| `data/jarvis5/` | 저장소에 올라가는 하루치 파일 |
| `db/jarvis5_theme_lead.sqlite3` | 노트북 로컬 DB. 저장소에 올리지 않는다 |

## 3. 손대기 전에 알아야 할 것

### 3.1 하루치 파일에 종목행 전체를 넣지 마라

하루 종목행은 약 83만 줄이다. 다 담으면 저장소가 감당하지 못한다(1년에 수 GB).
그래서 파일에는 이것만 담는다.

| 파일 | 내용 | 하루 크기(82회 기준) |
|---|---|---|
| `{날짜}.runs.csv.gz` | 수집 시각·간격 | 수 KB |
| `{날짜}.themes.csv.gz` | 테마행 전체 | 약 1.1 MB |
| `{날짜}.stocks.csv.gz` | **마지막 수집분 종목행만** | 약 0.16 MB |

마지막 수집분 종목행이 필요한 이유는 **다음 수집이 구간값을 이어서 계산하려면
직전 누적 거래대금이 있어야 하기 때문**이다(`store.previous_stock_snapshot`).
빼면 오전·오후 작업이 이어지지 않고 매번 첫 수집으로 취급된다.

### 3.2 gzip CSV에 유효숫자 8자리

같은 자료가 JSON이면 1.87MB, CSV+8자리면 0.81MB다(2026-07-24 실측). 8자리면
거래대금·비율 모두 사실상 손실이 없고, 실제 대조에서 어긋난 값이 없었다.
`jarvis5_sync.SIGNIFICANT_DIGITS`를 줄이면 파일은 조금 작아지지만 정밀도를 잃는다.

### 3.3 수집 id를 파일에 넣지 마라

`collection_runs.id`는 컴퓨터마다 다르게 매겨진다. 파일은 `captured_at`으로 묶고,
들여올 때 새로 매긴다. 덕분에 같은 파일을 여러 번 합쳐도 중복되지 않는다
(이미 있는 `captured_at`은 건너뛴다). 이 성질은 테스트로 지키고 있다.

### 3.4 스키마를 바꾸면 세 곳을 같이 고쳐라

`theme_snapshots`·`collection_runs`·`theme_stock_snapshots`에 칸을 추가하면
`jarvis5_sync.py`의 `_RUN_FIELDS`·`_THEME_FIELDS`·`_STOCK_FIELDS`도 같이 고쳐야
그 칸이 클라우드에 실린다. 숫자 칸이면 `_INT_FIELDS`·`_TEXT_FIELDS` 분류도 본다.

### 3.5 작업을 오전·오후로 나눈 이유

GitHub 작업 하나가 최대 6시간이라 09:00~15:35을 한 번에 못 덮는다. cron은 UTC라
한국시각에서 9시간을 빼서 적는다.

| cron | 한국시각 | 마치는 시각 |
|---|---|---|
| `55 23 * * 0-4` | 08:55 | 12:10 |
| `5 3 * * 1-5` | 12:05 | 15:35 |

`--until`은 한국시각 기준이며 수집기가 스스로 끝낸다.

### 3.6 파이썬 묶음은 최소로

클라우드 수집기는 네이버 HTML만 읽으므로 `requests`, `pandas`면 된다.
`requirements.txt`를 통째로 설치하면 streamlit·yfinance까지 받아 시간만 버린다.
단, `jarvis4_data`의 최상위 import가 늘어나면 여기도 같이 늘려야 한다.

## 4. 알고 받아들인 한계

- **예약 시작이 5~20분 늦을 수 있다.** GitHub 사정이며 우리가 못 고친다.
  늦게 시작해도 그 시점부터 3분 간격으로 모으므로 자료가 통째로 비지는 않는다.
- **종목 상세는 노트북을 켠 날 것만 쌓인다.** 3.1의 크기 문제 때문이다.
  화면의 테마 순위·미니차트는 테마행만으로 그리므로 영향이 없다.
- **한국 휴장일에도 작업이 돈다.** 누적값이 안 변해 구간값이 0으로 나올 뿐이라
  해롭지는 않다. 공개 저장소는 Actions가 무료라 비용도 없다.
- **저장소가 공개다.** 2026-07-24 사용자가 직접 전환했다. 전환 전에 확인한 것:
  코드에 비밀번호·토큰이 박혀 있지 않고(설정 이름만 참조), `db/*.sqlite3`와
  `.streamlit/secrets.toml`은 `.gitignore`로 막혀 있다.
  **앞으로도 비밀값을 코드에 직접 쓰면 안 된다.**

## 5. 확인 방법

```bash
# 하루치 내보내기·들여오기가 제대로 도는지
python -m unittest test_jarvis5_sync

# 실제 수집 한 번 → 파일 생성 → 다시 합치기 (임시 폴더에서)
python jarvis5_collector.py --once --db /tmp/t.sqlite3 --export-dir /tmp/out
python jarvis5_sync.py import --dir /tmp/out --db /tmp/t2.sqlite3
```

클라우드가 도는지는 저장소 **Actions** 탭에서 "자비스5 테마 수집" 실행 기록을 본다.
자료가 올라왔는지는 `data/jarvis5/` 폴더에 오늘 날짜 파일이 있는지로 확인한다.
